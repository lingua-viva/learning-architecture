# Update-System Research: Shipped Templates + User-Owned Artifacts

Research date: 2026-07-27. Scope: one-button install/update for a local-first Electron + Python app shipping YAML "lenses"/"canvases" that users customize, with user state in `~/.appname` (`lv_home()` seam). No code changes; web research + synthesis only. All claims grounded in cited, real systems.

---

## Q1. Package-manager patterns for classifying shipped / modified / user-created files

### dpkg conffiles (Debian)

- dpkg keeps an **md5sum database** of every conffile as shipped; on upgrade it compares the current file's hash against the stored one. Unmodified files are silently replaced with the new version; modified files trigger an interactive prompt. ([dpkg(1) man page](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html), [Raphaël Hertzog, "Everything you need to know about conffiles"](https://raphaelhertzog.com/2010/09/21/debian-conffile-configuration-file-managed-by-dpkg/))
- The prompt offers: **Y/I** install maintainer's version (old saved as `.dpkg-old`), **N/O** keep yours (new saved as `.dpkg-dist`), **D** show diff, **Z** shell. Default preserves the user's version. ([Hertzog](https://raphaelhertzog.com/2010/09/21/debian-conffile-configuration-file-managed-by-dpkg/))
- Non-interactive policy flags: `--force-confold` (keep local, write `.dpkg-dist`), `--force-confnew` (take new, save `.dpkg-old`), `--force-confdef` (take default action, prompt only when there is none), `--force-confask` (re-prompt even on reinstall for modified files). ([dpkg(1)](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html))
- **Deleted counts as modified**: a user-removed conffile is treated as a local modification and not resurrected. ([Hertzog](https://raphaelhertzog.com/2010/09/21/debian-conffile-configuration-file-managed-by-dpkg/), [Debian Policy Appendix: configuration file handling](https://www.debian.org/doc/debian-policy/ap-pkg-conffiles.html))
- **Renames/removals are NOT automatic**: dpkg has known limitations around conffiles that are renamed or dropped between versions; packages must explicitly call `dpkg-maintscript-helper rm_conffile` / `mv_conffile` in maintainer scripts, which themselves check the md5 first (modified → preserved as `.dpkg-backup` / left in place; unmodified → removed/renamed via a `.dpkg-remove` staging name so an aborted upgrade doesn't lose the file). ([dpkg-maintscript-helper(1)](https://manpages.debian.org/unstable/dpkg/dpkg-maintscript-helper.1.en.html), [Debian wiki: DpkgConffileHandling](https://wiki.debian.org/DpkgConffileHandling))
- **Documented failure modes**: obsolete conffiles linger forever unless explicitly removed; prompting mid-upgrade blocks unattended updates (hence the force flags); the md5 database can only classify files it knows about — anything outside the conffile list is invisible to the mechanism. ([DpkgConffileHandling](https://wiki.debian.org/DpkgConffileHandling), [Unix Memo: Debian package config](https://unix-memo.readthedocs.io/en/latest/debian_package_memo.html))

### RPM `%config` / `%config(noreplace)`

- Plain `%config`: on upgrade the **new file wins**; a locally edited old file is renamed `*.rpmsave`. `%config(noreplace)`: the **local file wins**; the new default is written as `*.rpmnew`. If a `%config(noreplace)` file is dropped from the package, the local copy is renamed `*.rpmsave`. ([J. Warbrick, "RPM, %config, and (noreplace)"](https://www.cl.cam.ac.uk/~jw35/docs/rpm_config.html), [RPM Guide §9.5.3](https://jfearn.fedorapeople.org/en-US/RPM/4/html/RPM_Guide/ch09s05s03.html), [JetPatch: rpmnew and rpmsave handling](https://kc.jetpatch.com/hc/en-us/articles/360043017992-rpmnew-and-rpmsave-handling))
- RPM performs the same three-way logic internally (original hash vs on-disk vs new): if the file is unmodified it is silently upgraded in both modes. ([eklitzke, "Handling Updated RPM Package Configuration Files"](https://eklitzke.org/handling-updated-rpm-package-configuration-files))
- Fedora's rule of thumb: use `%config(noreplace)` unless replacing is truly required — i.e., default to preserving user edits. ([fpm-cookery issue #118 quoting Fedora guidelines](https://github.com/bernd/fpm-cookery/issues/118))
- **Failure modes**: with plain `%config`, services silently start running the vendor config and the user's config sits unnoticed in `.rpmsave` ("silent-ish overwrite"); with `noreplace`, `.rpmnew` files silently accumulate and the running config drifts from what the new engine expects — the exact schema-drift hazard. Real-world example: OpenNebula had to file a bug to stop RPM upgrades replacing configuration. ([OpenNebula bug #3520](https://dev.opennebula.org/issues/3520.html), [eklitzke](https://eklitzke.org/handling-updated-rpm-package-configuration-files))

### pacman `.pacnew` / `.pacsave`

- Pacman compares three hashes (original as shipped, current on disk, new in package). Unmodified → silent upgrade. Modified + new default changed → local kept, new written as `.pacnew`. On package removal, modified configs saved as `.pacsave`. ([ArchWiki: Pacman/Pacnew and Pacsave](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave), [linuxiac guide](https://linuxiac.com/how-to-handle-pacnew-files-in-arch-linux/))
- Pacman **never auto-merges**; the wiki explicitly says users must handle `.pac*` files themselves, ideally right after every upgrade, and that leaving them unhandled can leave software misconfigured or unable to run. `pacdiff` (pacman-contrib) exists solely to find and interactively merge them. ([ArchWiki](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave), [linuxiac](https://linuxiac.com/how-to-handle-pacnew-files-in-arch-linux/))
- **Failure mode**: the "merge debt" problem — the mechanism is safe but pushes an unbounded manual-merge queue onto the user; on Arch this is accepted, in a consumer desktop app it is not.

### Cross-cutting takeaway (Q1)

All three converge on the same classifier: **hash-at-ship-time database + three-way compare**, differing only in conflict policy (prompt vs `.rpmnew` vs `.pacnew`). All three share two documented weaknesses: (1) renames/deletions of shipped files need explicit migration logic (dpkg-maintscript-helper); (2) the "park the new version beside the old" strategy creates silent drift unless something surfaces the parked files.

## Q2. How modern user-extensible apps handle shipped defaults + user overrides

### Overlay / precedence layering

- **VS Code**: defaults are a **read-only virtual file** (`defaultSettings.json`, opened via "Open Default Settings"); user `settings.json` is a sparse overlay containing only deltas. Precedence: default < user < workspace < folder < language-specific. Users literally cannot modify shipped defaults, so updates can change defaults freely and never conflict with user state. ([VS Code docs: User and workspace settings](https://code.visualstudio.com/docs/configure/settings), [Default settings reference](https://code.visualstudio.com/docs/reference/default-settings))
- **Anki add-ons**: shipped `config.json` holds defaults only; user edits go to `meta.json`, which is "not overwritten on updates"; missing keys fall back to defaults. Documented gotcha: if the developer changes a default in `config.json`, users who customized anything keep seeing old values until they "restore defaults" — sparse-overlay staleness. Larger user data goes in a `user_files/` folder that the updater is required to preserve. Add-on folders are named by **numeric AnkiWeb ID** to prevent namespace collisions. ([Anki add-on docs: Add-on Config](https://addon-docs.ankiweb.net/addon-config.html), [Add-on Folders](https://addon-docs.ankiweb.net/addon-folders.html), [Anki forums: config.json vs meta.json](https://forums.ankiweb.net/t/changes-in-add-on-config-made-through-anki-not-reflected-in-config-json/40812))
- **Game modding (Mod Organizer 2)**: the strongest overlay design — a **virtual file system** merges the vanilla game directory with per-mod directories at runtime; "no file ever gets overwritten when you install a mod and your data directory can remain in a vanilla state"; priority/load order is pure metadata. Game updates touch only the vanilla layer. ([STEP wiki: Mod Organizer/Advanced](https://stepmodifications.org/wiki/Guide:Mod_Organizer/Advanced), [ModdingLinked: MO2](https://themidnightride.moddinglinked.com/mo2.html))
- **WordPress child themes** (canonical web analogue): official docs state theme updates replace theme files, so direct edits are lost; child themes "keep customizations separate from the parent theme and allow parent themes to be updated without losing your modifications" — an overlay by directory precedence. ([WordPress Theme Handbook: Child Themes](https://developer.wordpress.org/themes/advanced-topics/child-themes/), [WPBeginner guide](https://www.wpbeginner.com/wp-themes/how-to-update-a-wordpress-theme-without-losing-customization/))

### App/data full separation (vault model)

- **Obsidian**: the vault is a plain folder of Markdown the user fully owns; app config lives in `.obsidian/` inside the vault; the application binary is entirely separate and updates never touch vault content. ([Obsidian Help: How Obsidian stores data](https://obsidianmd-obsidian-help.mintlify.app/files/how-obsidian-stores-data))
- **Home Assistant Container**: image (engine) and `/config` volume (user artifacts) are fully separated; updating = pull new image, config persists untouched; docs then tell you to check the logs/repairs for config incompatibilities — separation solves overwrite but NOT schema drift. ([HA docs: Common tasks – Container](https://www.home-assistant.io/common-tasks/container/), [HA docs: configuration.yaml](https://www.home-assistant.io/docs/configuration/))
- **HA blueprints** are copy-on-write template instantiation with namespacing: imported blueprints land under `/config/blueprints/<domain>/<source>/`, community docs warn "you shouldn't edit imported blueprints by hand, since a re-import would clobber your changes," and re-import-to-update has documented bugs (source_url not updated) plus a long-standing feature request for real upgrade support. ([Botmonster blueprint guide](https://botmonster.com/smart-home/home-assistant-blueprints-reusable-automations-explained/), [core#123025](https://github.com/home-assistant/core/issues/123025), [HA community: Allow blueprint upgrades](https://community.home-assistant.io/t/allow-blueprint-upgrades/366939))

### Copy-on-write / versioned instantiation

- **Blender**: per-version config dirs (`.../Blender/4.2/`); on first launch of a new version it offers to **copy** the previous version's settings forward; old versions' configs are never touched → free downgrade safety. Documented cost: the 4.2 add-ons→extensions transition meant blindly copying the old `addons` folder "will not work" — copy-forward migration breaks when the schema/layout changes. ([b3d.interplanety: transfer settings between Blender versions](https://b3d.interplanety.org/en/how-to-transfer-settings-and-add-ons-from-an-old-to-a-new-version-of-blender/), [Blender Artists: 4.2 copy settings](https://blenderartists.org/t/blender-4-2-copy-settings-from-previous/1539441))

### Verdict (Q2)

Overlay/precedence (VS Code, Anki, MO2, WordPress child themes) eliminates the conflict class entirely but only works when artifacts are *composable* (key-value merge or directory shadowing). Copy-on-write instantiation (HA blueprints, Blender startup files) is what you get when users must own a full editable copy — and every system doing it has a documented "re-import clobbers edits / no upgrade path" complaint. Your lenses are full documents users fork, so you are structurally in the second camp and need the Q1 three-way machinery for the shipped copies.

## Q3. Documented failure modes of in-place updates over user-customizable content

1. **Silent overwrite of user edits**: WordPress docs flatly state direct theme-file edits are lost on update ([Child Themes handbook](https://developer.wordpress.org/themes/advanced-topics/child-themes/)); HA blueprint re-import clobbers hand edits ([Botmonster](https://botmonster.com/smart-home/home-assistant-blueprints-reusable-automations-explained/)); electron-builder's autoUpdater overwrites/deletes anything shipped in `extraFiles`/`extraResources`, including files the app mutated ([electron-builder #4501](https://github.com/electron-userland/electron-builder/issues/4501)).
2. **ID/namespace collisions**: Anki solved shipped-vs-third-party collisions by assigning numeric AnkiWeb IDs as folder names and a `package` key in `manifest.json` for off-store add-ons ([Add-on Folders](https://addon-docs.ankiweb.net/addon-folders.html)); HA namespaces blueprints under a `<source>` subfolder ([Botmonster](https://botmonster.com/smart-home/home-assistant-blueprints-reusable-automations-explained/)). Absence of such namespacing is exactly what forces dpkg's "prompt on every collision" behavior.
3. **Schema drift (new engine, old artifacts)**: HA explicitly ships Repairs/log checks after container updates because config outlives the engine ([HA container tasks](https://www.home-assistant.io/common-tasks/container/)); unmerged `.pacnew`/`.rpmnew` files are documented as causing "application incompatibility... software unable to run" ([ArchWiki](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave), [linuxiac](https://linuxiac.com/how-to-handle-pacnew-files-in-arch-linux/)); Blender 4.2's addons→extensions layout change broke naive settings copies ([interplanety](https://b3d.interplanety.org/en/how-to-transfer-settings-and-add-ons-from-an-old-to-a-new-version-of-blender/)).
4. **Partial/interrupted update corruption + atomic staging solutions**:
   - Squirrel.Windows installs each version into its own `app-<version>` folder side-by-side, switches on next launch, and cleans old versions later — never patches in place. ([Squirrel update-process docs](https://github.com/Squirrel/Squirrel.Windows/blob/master/docs/using/update-process.md), [DeepWiki: The Update Process](https://deepwiki.com/Squirrel/Squirrel.Windows/3.2-the-update-process))
   - OSTree does whole-tree atomic deployments: the new root is fully staged, `/etc` is 3-way-merged, and the bootloader flip is the single atomic commit point; the merge itself is delayed until shutdown/reboot on staged deployments to avoid racing live edits. ([OSTree: Atomic Upgrades](https://ostreedev.github.io/ostree/atomic-upgrades/), [Deployments](https://ostreedev.github.io/ostree/deployment/))
   - dpkg-maintscript-helper stages via `.dpkg-remove` rename precisely so "if the package upgrade aborts, the newly obsolete conffile should not disappear." ([dpkg-maintscript-helper(1)](https://manpages.debian.org/unstable/dpkg/dpkg-maintscript-helper.1.en.html))
   - File-level primitive: write-temp → fsync → rename is the canonical crash-safe write; LWN documents that apps routinely get the fsync part wrong and lose data anyway. ([LWN: A way to do atomic writes](https://lwn.net/Articles/789600/))
5. **Downgrade hazards**: Firefox 67+ stamps profiles per-install and **refuses to open a profile last used by a newer version** (`compatibility.ini`; override only via `--allow-downgrade`/`MOZ_ALLOW_DOWNGRADE`) after downgrades corrupted user profiles ([Mozilla: Dedicated profiles](https://support.mozilla.org/en-US/kb/dedicated-profiles-firefox-installation), [Enterprise deep-dive](https://support.mozilla.org/en-US/kb/understanding-depth-profile-installation)); HA's config-entry docs state a **major** version bump makes the integration "fail setup if the user downgrades HA Core" while **minor** bumps must stay backward-compatible ([HA dev blog: minor versions](https://developers.home-assistant.io/blog/2023/12/18/config-entry-minor-version/)); Blender's per-version dirs sidestep downgrade entirely ([interplanety](https://b3d.interplanety.org/en/how-to-transfer-settings-and-add-ons-from-an-old-to-a-new-version-of-blender/)).

## Q4. Schema migration for user-owned YAML/JSON artifacts

- **Version fields + migration runner (Home Assistant)**: every `.storage` file carries `{"version": N, "minor_version": M, ...}`; storage helpers take `STORAGE_VERSION`/`minor_version` and a `_async_migrate_func(old_major, old_minor, old_data)`; config entries implement `async_migrate_entry`. Convention: minor bump = backward-compatible (old engine can still read it), major bump = one-way (downgrade fails setup). Migrations run at load time, i.e., on first launch of the new engine. ([HA dev blog: Config entry minor versions](https://developers.home-assistant.io/blog/2023/12/18/config-entry-minor-version/), [config_entries.py](https://github.com/home-assistant/core/blob/dev/homeassistant/config_entries.py))
- **Merge-with-defaults + version check (Obsidian plugins)**: the documented pattern is `Object.assign({}, DEFAULT_SETTINGS, await this.loadData())` so new keys get defaults and user values win, plus an explicit version number in the settings object with migration logic in load, then `saveData()` the migrated form; never edit `data.json` directly. ([Obsidian plugin docs: Settings](https://marcusolsson.github.io/obsidian-plugin-docs/user-interface/settings), [saveData reference](https://docs.obsidian.md/Reference/TypeScript+API/Plugin/saveData), [DeepWiki: Settings and Data Storage](https://deepwiki.com/obsidianmd/obsidian-api/3.4-settings-and-data-storage))
- **Fallback-to-default readers (Anki)**: `getConfig()` overlays `meta.json` on `config.json`, so missing keys degrade gracefully — a "keep old-schema readers" strategy; key renames need explicit migration code (documented forum pattern). ([Add-on Config](https://addon-docs.ankiweb.net/addon-config.html), [Anki forums: migrating config keys](https://forums.ankiweb.net/t/migrating-config-values-to-new-renamed-keys/57021))
- Practices to adopt: (1) `schema_version` in every artifact; (2) idempotent on-first-launch migration runner keyed on version; (3) validate-and-repair with defaults-merge for missing keys; (4) HA's major/minor split to encode downgrade compatibility; (5) migrate the *shipped* copies at build time and only run runtime migration on user-owned copies.

## Q5. Electron-specific update semantics

- **What survives**: only `app.getPath('userData')` (and other OS-level user dirs). Everything under the install dir — `app.asar` AND `extraResources`/`extraFiles` — is replaced or deleted by electron-updater/Squirrel on update. Documented explicitly in electron-builder issues: "if you modify an extra file, it gets modified when the app gets updated; if you delete a file from extra files, then the file gets deleted when the app is updated." ([electron-builder #4501](https://github.com/electron-userland/electron-builder/issues/4501))
- Conversely, partial-update mechanisms can leave `extraResources` stale ("binaries in extraResources are not automatically updated with asar"), so resources must be treated as fully owned by the updater in both directions. ([electron-builder #7781](https://github.com/electron-userland/electron-builder/issues/7781))
- Squirrel installs to versioned `app-<version>` folders side-by-side; anything an app writes inside its own install folder is stranded in the old version's folder after update. ([Squirrel update-process docs](https://github.com/Squirrel/Squirrel.Windows/blob/master/docs/using/update-process.md), [Squirrel #589 on leftover version folders](https://github.com/Squirrel/Squirrel.Windows/issues/589))
- On macOS, mutating anything inside the `.app` bundle breaks the code signature, and the `EnableEmbeddedAsarIntegrityValidation` fuse + `ElectronAsarIntegrity` Info.plist hash make runtime tampering with `app.asar` fatal by design — shipped resources must be immutable. ([Electron docs: ASAR Integrity](https://www.electronjs.org/docs/latest/tutorial/asar-integrity), [Electron Fuses](https://www.electronjs.org/docs/latest/tutorial/fuses))
- **Implication for us**: shipped lens/canvas templates inside app resources are a *read-only seed layer*; the live copies users see must be materialized under `~/.appname` (already true via `lv_home()`), and the update step that reconciles seed → live must run in app code on first launch of the new version, not in the installer.

## Q6. Critique of the proposed architecture (manifest + hashes + three-way compare)

**Verdict: this is the industry-consensus design.** It is literally dpkg's md5 database ([dpkg(1)](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html)), RPM's `%config(noreplace)` ([RPM %config](https://www.cl.cam.ac.uk/~jw35/docs/rpm_config.html)), pacman's pacnew logic ([ArchWiki](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave)), and — closest to our shape — OSTree's `/etc` three-way merge: "files modified from the default are retained; files not modified are upgraded to the new defaults." ([OSTree: Atomic Upgrades](https://ostreedev.github.io/ostree/atomic-upgrades/)). The `.new`-staging conflict policy matches `%config(noreplace)`/pacnew; never-touch-unknown matches all three; namespacing user artifacts matches Anki's ID-folder scheme and HA's blueprint source dirs.

Known pitfalls, each grounded:

1. **Manifest drift** — if any code path writes a shipped artifact without updating the recorded hash, the file is misclassified as user-modified forever (or worse, a stale manifest classifies user edits as unmodified and overwrites them). dpkg avoids this only because dpkg is the *sole* writer of its database; the moment two writers exist (our app + updater) the invariant needs a single owner. (Structural lesson from [dpkg(1)](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html) + the two-writer failure in [electron-builder #4501](https://github.com/electron-userland/electron-builder/issues/4501).)
2. **Shipped-artifact renames/deletions** — three-way compare alone cannot express "this template moved/died"; dpkg needed a whole helper (`rm_conffile`/`mv_conffile` with modified-check + crash-safe staging renames) ([dpkg-maintscript-helper(1)](https://manpages.debian.org/unstable/dpkg/dpkg-maintscript-helper.1.en.html)); RPM demotes removed configs to `.rpmsave` ([JetPatch](https://kc.jetpatch.com/hc/en-us/articles/360043017992-rpmnew-and-rpmsave-handling)). The manifest needs explicit `renamed_from:` / tombstone entries.
3. **User deleted a shipped template** — dpkg treats deletion as modification and does not resurrect ([Hertzog](https://raphaelhertzog.com/2010/09/21/debian-conffile-configuration-file-managed-by-dpkg/)). Without this rule, every update re-ships templates the user intentionally removed.
4. **Case-insensitive filesystems** — macOS APFS/HFS+ and Windows are case-insensitive/case-preserving; two artifact names differing only in case collide into one file (extensively documented for git checkouts) ([Adam Johnson: fix a filename case collision](https://adamj.eu/tech/2025/05/05/git-fix-filename-case-collision/), [Azure DevOps: Git case sensitivity](https://learn.microsoft.com/en-us/azure/devops/git/concepts/case-sensitivity)). A `user-` prefix scheme must compare case-folded; ship-side CI should reject case-colliding template names.
5. **Hash of YAML after reformatting** — dpkg/pacman hash raw bytes, so *any* rewrite (key reordering, quoting, trailing newline, CRLF, editor "format on save") flips a file to "modified" even with zero semantic change; the systems accept this false-positive (safe direction: prompt/pacnew, never overwrite). If the app itself ever round-trips shipped YAML through a serializer, every shipped file becomes "modified" and auto-update dies — either never rewrite pristine files, or hash a canonicalized parse. (Byte-hash semantics per [dpkg(1)](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html); drift consequence per [ArchWiki pacnew guidance](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave).)
6. **Symlinks** — hash the target vs the link? OSTree sidesteps by making the deployed tree hardlinked and immutable with only `/etc` mutable ([OSTree: Deployments](https://ostreedev.github.io/ostree/deployment/)). Simplest safe rule: forbid symlinks inside the managed template dir; treat any symlink as "user-modified, never touch."
7. **`.new` merge debt** — pacman's own wiki: unhandled `.pacnew` files "can result in improper function of the software or the software being unable to run," and tooling (`pacdiff`) had to be built to surface them ([ArchWiki](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave)). Ship an in-app "updates waiting" surface (our equivalent of pacdiff/HA Repairs), or conflicts rot silently.
8. **Interrupted reconcile** — updating N template files non-atomically can crash mid-way; use write-temp+fsync+rename per file ([LWN](https://lwn.net/Articles/789600/)) and a journal/two-phase marker like dpkg's `.dpkg-remove` staging ([dpkg-maintscript-helper(1)](https://manpages.debian.org/unstable/dpkg/dpkg-maintscript-helper.1.en.html)); make the manifest update the last, atomic step (OSTree's "single commit point" principle, [Atomic Upgrades](https://ostreedev.github.io/ostree/atomic-upgrades/)).
9. **Downgrade** — old engine + newer-schema user artifacts. Firefox refuses to open too-new profiles ([Mozilla](https://support.mozilla.org/en-US/kb/dedicated-profiles-firefox-installation)); HA encodes it in major/minor semantics ([HA dev blog](https://developers.home-assistant.io/blog/2023/12/18/config-entry-minor-version/)). Record `last_run_engine_version` + per-artifact `schema_version`, block or warn on downgrade.
10. **Namespace collisions with future shipped artifacts** — a user creates `finance-lens.yaml`, next release ships one with the same ID. Anki's numeric-ID folders and HA's `<source>` subdirectories both solve this by construction ([Add-on Folders](https://addon-docs.ankiweb.net/addon-folders.html), [Botmonster](https://botmonster.com/smart-home/home-assistant-blueprints-reusable-automations-explained/)). Reserve a shipped namespace (e.g., `lv-` / `shipped/` dir) and validate user IDs against it at creation time, not update time.

Additional design note: because Electron resources are updater-owned (Q5), the manifest + live templates must live in `~/.appname` (userData side), with app resources holding only the pristine seed set for the *current* version. First launch after update runs the reconcile. This is exactly Blender's "config outside the app, migrate on first launch of new version" shape ([interplanety](https://b3d.interplanety.org/en/how-to-transfer-settings-and-add-ons-from-an-old-to-a-new-version-of-blender/)) combined with OSTree's merge rules.

## Top 10 pitfalls ranked by likelihood

1. **App rewrites/reformats a pristine YAML → everything reads as "modified," auto-update silently stops working.** Resolution: never serialize back to shipped files; or store canonicalized-content hashes. (Byte-hash semantics: [dpkg(1)](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html).)
2. **Conflict files (`.new`) pile up unseen → schema drift, "app broke after update."** Resolution: build a pacdiff/HA-Repairs-style in-app review surface; treat unresolved conflicts as a visible health item. ([ArchWiki pacnew](https://wiki.archlinux.org/title/Pacman/Pacnew_and_Pacsave), [HA container tasks](https://www.home-assistant.io/common-tasks/container/))
3. **Manifest drift / two writers of truth.** Resolution: one module owns manifest writes; reconcile verifies manifest-vs-disk on every launch and self-heals by re-classifying conservatively (unknown → don't touch). (dpkg sole-writer model, [dpkg(1)](https://manpages.debian.org/testing/dpkg/dpkg.1.en.html).)
4. **New shipped template ID collides with a user-created artifact.** Resolution: reserved namespace for shipped IDs + creation-time validation (Anki numeric IDs, [Add-on Folders](https://addon-docs.ankiweb.net/addon-folders.html); HA source dirs, [Botmonster](https://botmonster.com/smart-home/home-assistant-blueprints-reusable-automations-explained/)).
5. **Shipped template renamed/removed upstream → orphans or duplicate templates.** Resolution: manifest tombstones + `renamed_from`, with modified-check before delete, mirroring `dpkg-maintscript-helper rm_conffile/mv_conffile` ([man page](https://manpages.debian.org/unstable/dpkg/dpkg-maintscript-helper.1.en.html)).
6. **Update writes templates into app resources (updater-owned) → user data destroyed or stranded on next update.** Resolution: all mutable state in `~/.appname`; resources are read-only seed. ([electron-builder #4501](https://github.com/electron-userland/electron-builder/issues/4501), [Electron ASAR integrity](https://www.electronjs.org/docs/latest/tutorial/asar-integrity))
7. **Old engine artifacts vs new engine (schema drift).** Resolution: `schema_version` per artifact + on-first-launch migration runner + defaults-merge for missing keys. ([HA minor versions](https://developers.home-assistant.io/blog/2023/12/18/config-entry-minor-version/), [Obsidian settings pattern](https://marcusolsson.github.io/obsidian-plugin-docs/user-interface/settings))
8. **Interrupted reconcile corrupts the template set.** Resolution: per-file temp+fsync+rename, staged pass, manifest commit last. ([LWN atomic writes](https://lwn.net/Articles/789600/), [OSTree atomic upgrades](https://ostreedev.github.io/ostree/atomic-upgrades/), [Squirrel side-by-side](https://github.com/Squirrel/Squirrel.Windows/blob/master/docs/using/update-process.md))
9. **Downgrade after schema bump.** Resolution: Firefox-style version stamp + refuse/warn (`compatibility.ini` model) and HA's major-vs-minor compatibility contract. ([Mozilla dedicated profiles](https://support.mozilla.org/en-US/kb/dedicated-profiles-firefox-installation), [HA dev blog](https://developers.home-assistant.io/blog/2023/12/18/config-entry-minor-version/))
10. **Case-insensitive filesystem collisions (and symlinks) in the managed dir.** Resolution: CI check rejecting case-colliding shipped names; case-folded comparisons at runtime; treat symlinks as user-modified/never-touch. ([Azure DevOps git case sensitivity](https://learn.microsoft.com/en-us/azure/devops/git/concepts/case-sensitivity), [Adam Johnson](https://adamj.eu/tech/2025/05/05/git-fix-filename-case-collision/))
